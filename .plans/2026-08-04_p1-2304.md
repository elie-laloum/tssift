# P1 / 2304 · 2552 — le pliage par nom manquant

**Livré le 2026-08-04.** Écrit pour un agent sans contexte : lire `AGENTS.md`
(règles dures) → `PROJECT.md` §5.1 (le seuil) → `EVAL.md` § P1/2304 (les
chiffres) → ce plan.

C'est une règle de **causalité**, pas un enrichisseur. Elle ne touche ni
`src/pipeline/enrich/`, ni `src/codes.ts`, ni la table des onze de §5.2.

---

## Pourquoi maintenant

§5.1 liste TS2304 en **racine quasi certaine** depuis l'origine, au même titre
que 2307, et sa règle était la moitié non écrite de cette liste. Elle est restée
non écrite parce que rien ne la rendait urgente : `fixtures/cannot-find-name`,
committée le 2026-07-28 pour chiffrer le manque, porte **un nom sur un site** —
donc son pliage 0 % était une propriété de la fixture, pas du code.

Le sondage sur `keyzia/data-explorer` du 2026-08-03 (`EVAL.md` § Real code) a
fourni le témoin qui manquait : **huit entrées pour quatre noms distincts**, six
des diagnostics dans un seul fichier, sur une sortie de générateur OpenAPI qui a
perdu ses types de requête. Même forme que 2307 avant T1 — la clé est le nom, et
aucune règle ne le lisait.

## La décision qui coûtait quelque chose : amender §5.1

§5.1 excluait **nommément** « même identifiant » et « même nom dans le même
fichier », et refusait d'appliquer sa propre règle de dérivation 3 pour cette
raison :

> « même nom dans le même fichier » n'est pas une identité — deux liaisons
> distinctes qui s'ombrent portent le même nom.

**La raison invoquée ne peut pas se produire ici.** L'ombrage demande au moins
une liaison ; `Cannot find name 'X'` est le compilateur affirmant qu'il n'y en a
aucune d'atteignable. L'interdit est écrit en général mais justifié par un
mécanisme structurellement impossible pour ces deux codes.

D'où une **exception étroite**, écrite comme telle dans §5.1 : l'interdit reste
entier pour les noms **liés** — la règle 3, 2339 — et les deux tests nommés qui
l'y tiennent (`does not group on the same name at a different position`, `… on
the same file and the same code`) sont **restés intacts et passent**, parce
qu'ils sont bâtis sur le code 2339 par défaut du helper synthétique. C'est la
preuve que le desserrage est étroit et non général, et c'est le desserrage que
§5.1 annonçait lui-même : *« on desserrera plus tard avec des chiffres »*.

## Ce qui a été tranché, et par qui

| décision | choix | raison |
|---|---|---|
| portée de la clé | **`(fichier, nom)`** | un identifiant est scope-local ; un spécificateur de module est global, donc la clé inter-fichiers de 2307 ne se transfère pas. Sous-regroupement assumé (§5.1). Ne coûte rien aujourd'hui : le vrai code comme la fixture sont mono-fichier |
| TS2552 | **même règle que 2304** | la leçon 2724 : le code émis dépend des noms voisins, pas de la panne |
| fixture | **`two-missing-names-one-file`** | aucune fixture ne prouvait que deux noms manquants distincts restent deux entrées |

Les trois tranchées avec l'humain avant écriture d'une ligne.

## Gabarits — lus, pas supposés

Extraits de `ts.Diagnostics` des trois compilateurs épinglés, **identiques** sur
5.4.5, 5.9.3 et 6.0.3 :

```
2304  Cannot find name '{0}'.
2552  Cannot find name '{0}'. Did you mean '{1}'?
```

Le motif est **ancré en début de chaîne** — `/^Cannot find name '([^']+)'/` — et
l'ancre porte : sans elle, un motif libre irait chercher la *suggestion* de 2552
comme clé. Un test le prouve plutôt que de le faire relire.

**TS2503 et TS2686 sont hors périmètre sur décision** : racines de §5.1 elles
aussi, mais aucune fixture, aucun témoin réel, gabarit différent. Un test nommé
le grave pour que ce soit une décision et non un oubli qu'on « corrige ».

**Le garde de correction est le `snippet`.** Il joue le rôle que
`ProgramFacts.imports` joue pour 2307 : recouper la lecture du message contre
autre chose que le message. Le nom doit être un identifiant simple **et** figurer
dans la ligne source relevée à l'ingestion. Absent ou contredisant ⇒ racine
isolée, jamais une fusion.

`missingName` n'est **pas exportée**, contrairement à `unresolvedSpecifier` :
celle-là l'est parce que l'enrichisseur 2307 doit rendre la même réponse. Il n'y
a pas d'enrichisseur 2304, donc l'exporter serait une surface publique que rien
ne consomme.

## Ce que ça a donné

À périmètre constant (27 cibles, la nouvelle fixture tenue à l'écart) :

| | entrées | B car. | B/A |
|---|---:|---:|---:|
| avant | 54 | 19 666 | 59 % |
| après | **48** | **19 514** | **58 %** |

**Les −152 caractères sont, au caractère près, le delta de `cannot-find-name`
seule** — aucune autre cible ne bouge d'un caractère. C'était la condition
d'arrêt annoncée : une règle indexée sur le nom qui déborderait de 2304/2552 se
verrait comme un mouvement ailleurs dans ce tableau.

- `cannot-find-name` : 7 entrées → **1**, 571 → 419 car., 116 % → **85 %** —
  **seconde fixture sous 100 %** après `narrowed-union-member`, et la première où
  c'est un diagnostic *court* qui dépasse le plafond par le seul nombre de sites.
- Pliage à cause unique : **12/18 → 13/18**, dénominateur inchangé (la nouvelle
  fixture est un témoin négatif, donc exclue). Trois liens structurels désormais.
- Sur le vrai code : 10 entrées → **6**, mais **+596 caractères** (68 % → 84 %),
  parce qu'aucun de ses quatre groupes n'a plus de deux membres et que les noms
  générés par OpenAPI font des en-têtes de ~140 caractères.

**La fixture et le vrai code sont en désaccord sur le signe, et les deux sont
publiés.** Le prédicteur est celui que ce dépôt répète depuis P1 : le nombre de
sites qu'une cause explique. Ce jalon est sa démonstration la plus nette parce
qu'il tombe des deux côtés de la ligne dans un seul changement.
