## Contexte minimal

Couche de post-traitement des diagnostics `tsc` pour un **agent** qui lance `tsc --noEmit` dans un shell. On regroupe par cause racine, on trie par pouvoir explicatif, on attache des faits vérifiables. **On ne dit jamais quoi corriger.**

Deux hypothèses : **H1** (réduire le bruit en cascade réduit faux départs et tokens — confiance forte) se construit d'abord ; **H2** (reformuler améliore la correction — confiance faible) ne se construit que sur les codes où l'éval montre un gain.

### Deux conséquences à ne pas prendre pour des bugs

**La sortie P0 est peu spectaculaire.** Mêmes messages que `tsc`, seulement ordonnés et annotés. Le pliage des cascades arrive en P1, l'enrichissement en P2. C'est l'ordre voulu : reformuler dès P0 rendrait H1 immesurable.

**La causalité sous-regroupera.** Le seuil de §5.1 est volontairement strict. Les premiers chiffres seront plus modestes qu'une règle lâche ne le permettrait. Sur-regrouper cacherait une vraie erreur — l'échec que §11 classe *critique*.

## T2 · Les trois fixtures

**Objectif.** Le contrat de sortie, rendu concret **avant** tout code moteur.

`meta.json` + `before/` seulement. Pas de `after/` : il n'aura de consommateur qu'à B1.

### `fixtures/partial-interface-rename/`
L'exemple de PROJECT.md §6. `src/types/user.ts` déclare `CreateUserInput { id: string; email: string; name?: string }`. `src/api/user.ts` utilise `emial` à trois endroits, produisant **2353**, **2339** et **2345** — ce dernier avec une `messageChain` et un `relatedInformation` pointant vers la déclaration.

### `fixtures/two-independent-roots/`
**Le témoin négatif, obligatoire.** Deux racines réellement indépendantes : aucun import entre les deux fichiers, aucun symbole partagé, aucun `declaredAt` commun. Par exemple un `2307` sur un module absent dans un fichier, et un `2339` sur un type déclaré localement dans l'autre. Zéro faux positif de causalité dessus est un critère de la DoD — la fixture n'a de valeur que si l'indépendance est réelle et non simplement plausible.

### `fixtures/overload-mismatch/`
Une fonction à trois surcharges appelée incorrectement ⇒ **2769**, avec une `messageChain` d'au moins trois niveaux et plusieurs `relatedInformation`. C'est le seul témoin de rendu de chaîne profonde, et le rendu de chaîne se fige maintenant.

**Configuration** — chaque `before/` porte le bloc canonique complet d'AGENTS.md § « Recette — ajouter une fixture », **sans `extends` sortant du dossier**. Une copie de `before/` doit rester exécutable telle quelle : le bras A de l'éval en dépend.

**`scripts/verify-fixtures.mjs`** — pour chaque fixture, exécute le `tsc` de `typescript@5.9.3` **et** celui de `typescript-5.4` sur `before/`, et échoue si l'un des deux sort en 0. Une fixture qui compile n'est pas une fixture.

**Critères d'acceptation**
- [ ] Les trois `before/` échouent sous **5.4.5 et 5.9.3**
- [ ] `overload-mismatch` produit une chaîne d'au moins trois niveaux (vérifier à la main, une fois)
- [ ] `two-independent-roots` n'a aucun import ni symbole commun entre ses deux racines
- [ ] Chaque `meta.json` a `rootCause`, `expectedFix`, `tags`, `difficulty`

## T5 · `src/sources/` — l'ingestion

**Objectif.** `DiagnosticSource` et `TsApiSource`. C'est la seule couche autorisée à voir `typescript`.

### `sources/index.ts`
```ts
interface DiagnosticSource {
  load(opts: { project: string; captureFor: readonly number[] }):
    { diagnostics: NormalizedDiagnostic[]; facts: ProgramFacts };
}
```

### `sources/ts-api.ts` — dans cet ordre

1. **Résolution du peer.** `createRequire(<dossier du tsconfig>/)` → `require.resolve('typescript')`. Introuvable ⇒ **sortie 2**, en nommant ce qui a été cherché et où.
2. **Garde de version.** Hors `>=5.4 <6` ⇒ **sortie 2**, message nommé, mentionnant la version résolue et son chemin. Pas de repli (règle 15).
3. **Chargement du projet.** `readConfigFile` + `parseJsonConfigFileContent`, puis `createProgram`. Le dossier du tsconfig résolu devient la **racine** de tous les chemins.
4. **Diagnostics.** `getPreEmitDiagnostics()` uniquement.
5. **Normalisation** :
   - offsets → `line`/`column` **1-indexés**, via `getLineAndCharacterOfPosition`, converti une seule fois
   - `file` relatif à la racine, séparateurs **POSIX** ; hors racine : `<ts-lib>/lib.es5.d.ts` pour les libs TypeScript, suffixe `node_modules/…` depuis la racine de paquet la plus proche
   - `message` : `flattenDiagnosticMessageText` du seul nœud de tête, **jamais altéré**
   - `chain` : parcours **préfixe** avec `depth`, `code` conservé par nœud
   - `related` : `{ span?, message, code? }` — le texte est obligatoire, le span non
   - `snippet` : la ligne source, trim
   - `id` : `sha256(code|file|line|col|message)`, 12 premiers hex
   - `context` : résolu **uniquement** pour les codes de `captureFor` (donc jamais en P0)
6. **`ProgramFacts`** : `root`, `files` (relatifs), `imports` (fichier → spécificateurs résolus), `typescript: { version, path }`.
7. **Ordre déterministe.** Trier par `(file, line, column, code)` avant de rendre. Sans tri explicite, l'ordre dépend de l'ordre du programme et les snapshots deviennent instables — panne coûteuse à diagnostiquer plus tard.

**Critères d'acceptation**
- [ ] Sur `partial-interface-rename`, trois diagnostics aux codes attendus
- [ ] Le 2345 porte une `chain` non vide **et** un `related` avec un `message` non vide
- [ ] Aucun chemin absolu, aucun `\` dans un `SourceSpan.file`
- [ ] Deux exécutions consécutives donnent des `id` identiques et le même ordre
- [ ] Un projet en TS 7 sort en 2 avec le message nommé
- [ ] `src/pipeline/` n'existe pas encore, ou n'importe pas `typescript`

**Vérification** — `mise exec -- bun run test`
**Commit** — « feat: TsApiSource, normalization, ProgramFacts »

## Pièges connus

- **`bun run --bun` est proscrit.** Il court-circuite le shebang et fait tourner les tests sous bun au lieu de Node, silencieusement.
- **Aucun binaire par chemin absolu.** Il existe un bun hors mise dans `~/.bun` et un Node système : les viser donne une autre version sans le moindre message.
- **`fixtures/` doit être exclu** de notre tsconfig, de Biome et de la découverte vitest — sinon nos propres commandes échouent sur du code cassé exprès.
- **Chemins de `lib.d.ts` dans les snapshots.** Un `relatedInformation` peut pointer vers `/home/<user>/…/typescript/lib/lib.es5.d.ts`. Non normalisé, il tue le snapshot sur toute autre machine.
- **Ordre des diagnostics.** Trier explicitement, sinon l'ordre du programme fait varier les snapshots.
- **Ne jamais régénérer un snapshot en aveugle.** Le diff se lit ; c'est le filet de sécurité du projet.
- **Ne jamais présumer un `node_modules/`**, ne jamais invoquer un gestionnaire de paquets en sous-processus (règle 10).
- **Aucune dépendance runtime** ajoutée sans justification écrite.
- **`NodeNext` + extensions `.js` pour notre `src/`**, `Bundler` sans extensions pour les fixtures. Ne pas croiser les deux.
